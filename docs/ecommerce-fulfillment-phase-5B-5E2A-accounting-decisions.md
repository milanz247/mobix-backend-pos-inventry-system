# Phase 5B.5E2A — Ecommerce handover accounting decisions

**Status:** read-only source analysis, 2 November 2026. This document records recommendations for approval; it does not authorize tax treatment, schema changes, payment posting, handover, or rollout. Read with [the Phase 5B.5D contract](ecommerce-fulfillment-phase-5B-5D-implementation-contract.md), [the fulfillment record](ecommerce-fulfillment-phase-5B-5.md), and [the order/reservation record](ecommerce-order-reservation-phase-5.md). Source was inspected; no database schema or live records were queried. The E1 migrations remain unverified on isolated MySQL.

## 1. Current implementation findings

| Area | Actual source and behavior | Consequence for E2 |
| --- | --- | --- |
| Product tax | `app/Services/SaleService.php::checkout`, `includedTax` allocate the business's current `tax_rate` to each discounted product line using `line_total × rate / (100 + rate)` with `BigDecimal` and half-up rounding. `sale_lines.tax_total` and `sales.tax_total` store the included amounts. `app/Models/Business.php` and `app/Http/Requests/Settings/UpdateBusinessSettingsRequest.php` expose one business-level rate (0–100, two decimals); migration `2026_10_31_000001_add_shop_operations_controls.php` added it. The invoice's `invoice_show_tax` setting controls display, not calculation. | Prices are presently treated as tax-inclusive. There is no fee-specific tax class, charge tax snapshot, or verified delivery-fee tax rule. No current setting proves what tax applies to delivery. |
| Sale totals | `SaleService::checkout` adds `sale_lines.subtotal`, subtracts line and order discounts, and stores `sales.subtotal`, `discount_total`, `tax_total`, `total`, `paid_total`, `payment_status`. `SaleService::paymentStatus` derives unpaid/partially_paid/paid from actual net paid against net sale total. `app/Services/StorefrontOrderOfferService.php` currently calculates accepted web `total = product subtotal + delivery_fee` with `discount_total = 0.00`; `StorefrontOrderSubmissionService.php` rechecks and snapshots those values in `web_orders` and `web_order_items`. | The accepted total includes a separate fee, while the POS sale total currently has only product-line arithmetic. E2 must reconcile the exact accepted total without repricing it. |
| Additional charges | Base sales migration `2026_10_16_041407_create_sales_and_returns_tables.php` has sale lines, components, payments and returns, but no `sale_charges` or `delivery_fee` on sales. `2026_10_30_000002_create_sale_additions_table.php` is **not** a charge table: `SaleService::checkout` uses it to add items to existing credit sales. `sale_lines.product_variant_id` is required. | A delivery fee cannot be safely represented by an existing sale addition or a fake stock product. A typed, non-inventory charge needs an additive schema and sale-total/report support if approved. |
| Payments | `SaleService::checkout`, `recordPayment`, `preparePayments`, `paymentCashDetails`, and `SalePaymentStatus` record immutable `sale_payments` with `method`, `amount`, `reference`, `paid_at`, real `received_by`, optional `cashier_shift_id`, `operation_key`, cash tender/change. `RecordSalePaymentRequest` allows cash/card/bank_transfer/other. A payment can be posted later through `recordPayment`. | Existing generic payment writers do not distinguish a new receipt from a projection of money already verified for a web order; the bridge must guard this path against duplicate web bank/COD collection. |
| Invoice/receipt | `app/Support/SalePageData.php::sale` builds a sale DTO with product/component snapshots, tax, paid total and payments. `resources/js/components/sales/InvoiceDocument.vue` renders both A4 and 58/80 mm thermal layouts, shows `Subtotal − Discount`, optional `Tax included`, then `Total`, payments and optional IMEI. `resources/js/pages/sales/Receipt.vue` prints that document. `resources/js/types/invoice.ts` has no charge or public web-order reference field. | Both layouts and DTO/types need a distinct delivery-fee line and web reference. Current arithmetic display will not explain a sale total that includes delivery. IMEI is currently printable; web issued-invoice visibility still needs approval. |
| Shifts and drawer | `app/Http/Controllers/Sales/PosController.php::checkout` calls `SaleService::checkout(..., requireActiveShift: true)`. The service's default is false; it calls `CashierShiftService::activeId`, which locks the real cashier user and returns an open same-location shift or null. Migration `2026_10_19_095733_create_cashier_shift_tables.php` makes shift links on sales/payments nullable. `CashierShiftService::summary` groups all linked sale payments by method but increases `expected_cash` only for cash payments, less cash refunds and cash movements. | Normal POS checkout requires a shift. An E2 web bridge must make its own explicit shift rule. Bank payments must not enter physical drawer cash. Shop cash needs a real collector and reconciliation. |
| Reporting | `app/Services/SalesActivityService.php::query` uses `sales.total` in sale activity; `lines` uses product `sale_lines`. `app/Http/Controllers/DashboardController.php::__invoke` calculates gross profit from `line total − included tax − cost × quantity`; cash received sums `sale_payments` with method `cash`. `CashierShiftService::summary` counts sales linked to the shift. | A sale total with a fee can enter gross sales, but fee revenue/tax/cost and profit breakdown will be absent from line-based calculations unless reports are extended. A projected bank payment must be treated as a link to the prior receipt in receipt reporting. |
| Web payment evidence | Migration `2026_11_01_000005_add_web_order_submission_fields.php` creates one `web_order_payments` obligation per order (`method`, `status`, `currency`, `amount_due`). Migration `2026_11_01_000007_create_web_bank_transfer_evidence.php` creates immutable attempts (customer reference, optional amount/date, private evidence path) and one staff decision per attempt (`decision`, `received_amount`, `actor_user_id`, `actor_name_snapshot`, `reviewed_at`). `app/Services/WebBankTransferService.php::submit` makes proof awaiting verification, and `review` sums prior `underpaid` and `verified` decisions; only an exact remaining amount sets `paid_verified`. Excess is `overpayment_review`/manual review. | A proof or customer reference is not a receipt. Staff verification records received money, but there is no bank statement/settlement ledger or guaranteed bank receipt timestamp. Several accepted decisions can make one fully paid order. Preserve all attempts and decisions. |
| Bank order confirmation | `app/Services/WebOrderStaffService.php::confirmBank` checks `paid_verified`, exact decision sum, no unresolved proof, then creates `web_order_bank_confirmations` (migration `2026_11_02_000003_create_web_order_bank_confirmations.php`) and `web_order_status_histories` with reason `bank_order_confirmed`. `WebOrderPreparationService` requires that confirmation and verified payment before preparation. | Confirmation is an order authorization, separate from the bank receipt. Handover must check both and must not re-mark payment paid. |
| E1 bridge foundation | `app/SaleSource.php` contains `ecommerce`. `app/Models/Sale.php` requires that source and `web_order_id` occur together; additive migration `2026_11_02_000004_add_web_sale_bridge_foundation.php` proposes a unique business/web-order sale link and `web_order_fulfillments` unique per order/sale/operation, with actor, mode, inventory operation and handover time. `app/Models/WebOrderFulfillment.php` has relationships only; no posting service exists. The same migration adds nullable, unique `sale_payments.web_bank_transfer_decision_id` and a same-business FK. | Linkage and provenance **schema source** exist, but no handover, payment projection or sale-charge writer exists. These constraints have not been verified by a MySQL migration run. The FK alone does not validate that a decision belongs to the same order as the sale; service checks are required. |
| Reservations | `app/Services/WebReservationService.php::consumeForFulfillment` locks business/order, active reservations, quantity pools and exact devices; it transitions reservations to consumed, invokes a stock callback and checks physical deltas/device sold states. Its current precondition is order `confirmed`, and it sets order status `fulfilled`. `WebOrderPreparationService` uses `preparing`/`ready`; the approved handover boundary is actual pickup/courier handover. | This primitive cannot be called unchanged for a ready order. E2 must adapt it deliberately inside one outer handover transaction, keep exact-reservation stock checks, and leave customer journey status to a separate handover event. No consumption occurs in E2A. |

## 2. Decisions for approval

All recommendations below are **unapproved**. Approved first-release fulfillment modes remain bank transfer with home delivery and COD with shop pickup; courier COD is disabled. Physical stock consumption at actual handover is already approved.

| Decision | Current application behavior | Available options | Recommended option | Business approval required? | Implementation impact |
| --- | --- | --- | --- | --- | --- |
| A1. Delivery-fee tax treatment | Only product-line inclusive tax from current `businesses.tax_rate`; no fee tax class. | Fee taxable within accepted fee; fee exempt; jurisdiction/area-specific treatment. Tax added *on top* would change the accepted total and therefore needs a new quote/offer contract, not a handover adjustment. | Obtain accountant-approved tax classification and effective rule before any bridge posting. Preserve the customer's accepted total. | **Yes, accountant/business.** | Persist fee tax basis/rate/amount snapshot if applicable; validate `product + fee` tax and immutable total with decimal math. Block inconsistent or legacy accepted terms rather than silently reprice. |
| B1. Delivery-fee invoice form | No delivery charge schema or DTO; sale lines require a variant. | Dedicated typed sale charge; explicitly non-stock service line with supported tax/report semantics; omit from invoice (unacceptable for reconciliation). | Separate `Delivery Fee` sale charge, not a product line. | **Yes, presentation/accounting approval.** | Add `sale_charges` (or equivalent) with business/sale, type, accepted amount and tax snapshot; update sale total reconciliation, `SalePageData`, `InvoiceSale`, A4/thermal renderer, sales/return reports. No inventory or fake SKU. |
| C1. Shop COD collection | POS checkout requires an open cashier shift; web handover writer absent. Drawer expectation rises only on cash `sale_payments`. | Collect once in handover transaction with a real open shift; separate later collection with an unpaid sale/receivable; no shift with separate cash-control ledger. | Collect full accepted cash at actual pickup handover, linked to a real collector's open same-location shift. If no shift, reject handover before sale/stock changes. | **Yes, business.** | Add unique COD collection origin/operation; atomic sale + cash payment + web obligation update + reservation/stock handover; validate tender/change and partial-payment policy. No expected cash before handover. |
| C2. Bank sale and shift | Shift links are nullable; summary groups non-cash by method but excludes them from expected drawer cash. | Require shift for every web sale; require shift only for physical cash; separate non-cash web reporting. | No drawer shift for verified-bank courier handover; still use a real authorized handover actor and source-based sales reporting. | **Yes, business/accounting.** | Keep bank sale/payment shift IDs null; audit actor/location; ensure business sales and payment reports include unshifted Ecommerce sales without counting bank as drawer cash. |
| D1. Verified-bank projection | Web decisions prove staff-recorded receipts; E1 adds unique nullable decision FK on `sale_payments`, but no projection writer. | Project each accepted decision to a linked, non-cash sale payment; use an independent web-payment ledger and teach all sale reports to read it. | One provenance-linked `sale_payments` **allocation** per accepted `underpaid`/`verified` decision, only after checking exact aggregate due; never call it a new receipt. | **Yes, accounting approval for ledger/report semantics.** | Lock obligation/decisions, check same business/order/currency and no pending/overpayment; unique decision FK and operation key prevent replay; sale paid total reflects original verified money; web status and confirmation audit stay unchanged. Distinguish projection from bank receipt in reports. |
| D2. Bank receipt attribution | Decision has nullable actor FK and name snapshot, `reviewed_at`; customer attempt has reference up to 180 chars and optional transfer date. `sale_payments` requires `received_by`, `paid_at`, and reference max 100. | Require an active verifier and defined payment timestamp/reference; extend projection schema/DTO to preserve full source data; use a dedicated ledger link without forcing a misleading `SalePayment`. | Resolve attribution and date/reference mapping before projection; never assign the handover actor as if they verified the bank money or truncate the customer reference. | **Yes, accounting/operations.** | Potential additive fields or separate provenance DTO; decide whether verified time is the posting time, retain full original attempt/decision links, handle deleted verifier or older records as manual reconciliation. |
| E1. IMEI on issued invoice | `SalePageData` and A4/thermal `InvoiceDocument.vue` currently print serialized IMEI when present. Public web tracking does not. | Show on controlled issued invoice; omit; show only in an authenticated warranty document. | Obtain a customer-document policy before issuing web invoices. | **Yes, business/privacy.** | Invoice DTO/renderer policy only; never add IMEI to public tracking. |

No tax rate, tax exemption, fee cost, COD tender/change policy, or bank receipt timestamp is approved by this document. The existing business tax setting is a calculation input for POS product lines, not evidence of delivery-fee tax treatment.

## 3. Proposed accounting flows (pending approvals)

### Bank Transfer + Home Delivery

1. Keep the accepted web offer/order product subtotal, delivery fee and final total immutable. The customer proof attempt is evidence only. Authorized staff `WebBankTransferService::review` records actual received amounts; the final exact remaining decision sets `paid_verified`. A separate `WebOrderStaffService::confirmBank` audit confirms the order. Preparation may follow; none of these steps creates a POS sale or consumes stock.
2. At **actual courier handover**, a future authorized service locks the real actor/business/order/payment/confirmation, exact reservations and physical stock. Require `ready`, one eligible location, complete active reservations, exact verified sum equal to `web_order_payments.amount_due`/accepted total, and no unresolved proof or overpayment. Reject before mutation if fee tax/charge policy cannot reproduce the accepted total.
3. In one transaction create one Ecommerce sale linked by `sales.web_order_id`, accepted sale-line snapshots, approved typed delivery charge, one inventory operation, consumed reservations and one `web_order_fulfillments` row. Project each accepted bank decision at most once into the POS sale ledger using `sale_payments.web_bank_transfer_decision_id` **only if the approved reporting semantics prevent duplicate receipt counting**. Do not receive money again, change web payment state, create shop cash, or require a fictitious cashier shift. Customer delivery confirmation later changes journey status only.
4. Preserve the original attempts, staff decisions, bank order confirmation and their timestamps. The sale's paid status is a projection of previously verified money; the order/payment state remains separate. Any failed insert or stock posting rolls the whole handover back.

### COD + Shop Pickup

1. Staff phone confirmation with recorded `answered_confirmed` precedes `confirmed`; preparation and ready leave payment `cod_due` and stock physically unchanged. The selected pickup shop is the order's one accepted location.
2. At **actual customer handover**, the future service requires a real authorized collector and, if C1 is approved, that user's open same-location cashier shift. If absent, stop without posting a sale, cash payment, stock movement, reservation transition or order history. Validate actual tender before posting; do not count the order as drawer cash beforehand.
3. In one transaction record the physical cash once, create a unique COD collection origin and one Ecommerce sale, consume exact reservations and stock, post fulfillment identity, update the web COD payment state through an authorized collection event, and set the customer journey state. `sale_payments.method = cash` links to the real shift; `CashierShiftService::summary` then includes it in expected drawer cash. A duplicate request returns the committed result or a conflict under the unique keys, never another collection/sale.

## 4. Open decisions before atomic handover

1. **Accountant/business:** Is home-delivery fee taxable, exempt, or conditional? If taxable, is tax already included in the accepted fee? What effective tax rule and invoice wording apply? If an exclusive tax must increase customer total, update offer/acceptance before handover; do not add it to an existing accepted order.
2. **Business/accounting:** Approve a distinct Delivery Fee charge and how fee revenue, any delivery cost, fee tax, partial returns and refunds appear in sales/profit reports and A4/thermal documents.
3. **Business:** Approve mandatory open same-location cashier shift, full cash collection and tender/change handling for COD pickup. Define behavior for short cash or unavailable shift; the recommended default is to block handover.
4. **Accounting:** Approve bank decision-to-sale-payment projection semantics, receipt date and reference mapping, real verifier attribution, and reporting that counts a bank receipt once. Decide how to reconcile historical decisions whose actor FK is null. The original customer transfer reference can exceed `sale_payments.reference` length.
5. **Business/privacy:** Decide whether IMEI appears on an issued Ecommerce invoice. It must stay absent from public tracking regardless.
6. **Operations:** Define required courier handover evidence/reference and any issued-invoice timing. Courier COD remains disabled.
7. **Rollout:** Configure approved expiry policies separately and verify E1 migrations, full feature/regression suite and independent-connection MySQL contention on a demonstrably isolated database before enabling order submission. These are technical gates, not accounting approvals.

## 5. Phase 5B.5E2 implementation checklist after approval

- Record signed accounting decisions and testable acceptance examples, including tax-inclusive arithmetic and exact accepted-total reconciliation.
- Verify all existing Phase 5/E1 migrations and constraints on isolated MySQL; run POS regressions and genuine concurrent reservation/POS tests. Keep active POS data untouched.
- Add the approved typed delivery-charge schema and tax snapshot; preserve accepted web totals and business scope. Add COD collection provenance with unique origin. Verify the existing E1 sale, fulfillment and bank-decision constraints and fix only proven issues additively.
- Update sale DTO, `InvoiceSale`, A4/thermal renderer and source-aware revenue/profit/payment reports; explicitly separate verified receipt from sale allocation and drawer cash.
- Build a dedicated authorized web handover service using a real actor and the established business-row lock. Adapt `WebReservationService::consumeForFulfillment` for `ready` and customer journey states without weakening exact stock/device checks; keep sale, payment allocation/collection, inventory operation, fulfillment identity and status history in one transaction.
- Guard generic sale payment/add-item paths from creating duplicate or unauthorized web sale payments or edits. Preserve accepted snapshots, bank evidence, phone/bank confirmation records and stock movement audit.
- Test exact quantity, serialized and combo consumption; fee/tax/invoice arithmetic; one sale and one payment origin per order; bank underpayment/overpayment blocks; shift/drawer reconciliation; response-timeout retry; rollback on last component/payment insert; authorization; and independent MySQL contention. Do not treat SQLite or sequential tests as lock proof.
- Keep `STOREFRONT_ORDER_SUBMISSION_ENABLED=false` until the rollout gates, business decisions and end-to-end checks are complete. Do not implement courier COD in the first release.
