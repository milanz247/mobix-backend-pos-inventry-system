**Status:** planning only, 2 November 2026. This document proposes later work; it does not authorize stock consumption, sale creation, payment collection, or feature activation. Read with [the Phase 5 order and reservation record](ecommerce-order-reservation-phase-5.md), especially sections 17–22. ## 2. Lifecycle proposal and invariant

One order and one selected fulfillment location are retained throughout. Each action is a named server-side command with a specific permission and append-only audit entry; no generic status editor. Suggested permission names below are **proposals**, not existing grants. Location access and business scoping apply to every staff action. Inventory stays physically on hand and reserved through preparation and readiness.

| Transition / stage | Actor and proposed permission | Gate and reservation | Stock / sale | Customer-safe message and audit |
| --- | --- | --- | --- | --- |
| `pending_confirmation` | Customer submission; existing API | Complete active reservation, accepted offer; COD `cod_due` or bank awaiting proof | No deduction, no sale | Received; staff confirmation or payment review pending. Existing submit event. |
| `pending_confirmation -> confirmed` | COD: real staff caller with existing `storefront.confirm-orders`. Bank: **unapproved decision**; if required, separate authorized action. | COD confirmed call before deadline. Bank must have `paid_verified` before any preparation; exact bank confirmation gate awaits approval. Complete active allocation. | None | Confirmed; actor, time and reason in history. |
| `confirmed -> preparing` | Assigned staff, proposed `storefront.prepare-orders` | Valid complete reservation, selected location, COD call confirmed or bank verified and any additional bank confirmation satisfied. Hold/extension policy must be approved if reservation deadline has passed. | None | Preparing; picking actor/time, internal pick notes separate. |
| `preparing -> ready` | Assigned staff, proposed `storefront.mark-ready` | Picked exact reserved devices/components and checked quantity/condition; reconciliation if mismatch. | None | Ready for handover/dispatch; pick checklist and actor recorded. |
| `ready -> dispatched` (delivery) | Authorized handover staff, proposed `storefront.dispatch-orders` | Carrier handover evidence and exact allocation; payment gate. **Proposed stock-consumption boundary**, subject to approval. | Atomically consume reservation, post stock and sale once. COD remains unpaid unless real collection occurred. | Dispatched; handover time/reference, sale link and actor. |
| `ready -> delivered` (pickup) | Authorized handover staff, proposed `storefront.handover-orders` | Customer handover; pickup must first be approved as a release channel. | Same atomic posting as dispatch; cash collection, if present, is a separate exactly-once event. | Delivered/collected; actor and receipt. |
| `dispatched -> delivered` | Authorized delivery coordinator or approved carrier event | Verified delivery proof; no second stock or sale posting. | None | Delivered; timestamp and evidence reference. |
| `pending_confirmation/confirmed/preparing/ready -> cancelled` | Authorized staff, proposed lifecycle-specific cancel permission | Only when policy allows, no stock posting/consumed reservations, payment evidence reconciled. Current implementation only permits declined pending COD; expansion needs approval. | Release all active reservations atomically; no sale. | Cancelled with safe reason; private detail in staff audit. |
| `pending_confirmation -> expired` | Existing scheduler/system | Existing explicit COD/no-proof bank deadline only, no protected payment evidence. | Release active reservations; no sale. | Expired with system event. Confirmed orders are protected by current code. |
| `dispatched/delivered -> failed_delivery/return_requested/returned` | Future authorized workflow | Requires proof, parcel inspection, money and return policy. Do **not** map to ordinary cancellation/release. | Sale return/stock return only through audited process. | Accurate parcel/return status; audit. |

`fulfilled` is presently the terminal state set by `consumeForFulfillment`, while the requested customer lifecycle includes `dispatched` and `delivered`. The implementation phase must decide whether `fulfilled` is a separate *stock posting flag/event* alongside order state or a later terminal state. **Recommendation:** keep order state as the customer journey (`dispatched`/`delivered`) and record a unique fulfillment posting record with `consumed_at`, sale ID and inventory-operation ID. Do not set `fulfilled` at dispatch if delivery remains pending. This requires a deliberate revision of `consumeForFulfillment` and its tests, not a silent status override.

## 3. Physical stock and sale handoff

| Option | Benefit | Risk |
| --- | --- | --- |
| A. Preparation starts | Early book-out | Wrongly records a sale while items may still be repicked or cancelled; return/reversal needed for abandoned preparations. |
| B. Ready | Pick completed | Still may not leave business custody; cancellation requires sale return instead of reservation release. |
| C. Verified handover to carrier/customer | Aligns book-out with custody transfer | Requires precise handover action and delivery exception handling. |

**Recommended, unapproved:** C. Preserve physical on-hand and active reservation through `preparing` and `ready`. At verified handover, one transaction consumes this order's exact reservations, writes the sale/inventory operation and links them. Sale posting may precede customer receipt of a parcel; later failed delivery becomes a controlled return/reconciliation, not reservation release. COD remittance may happen much later than handover. A pickup handover would use the same boundary if pickup is approved.

Proposed `WebOrderFulfillmentService` should orchestrate an explicit `WebSaleBridge` and focused reservation-aware inventory posting methods. Reuse existing **record formats and calculation helpers** for stock movements, serialized events, costs, included tax and receipts. Do not pass a synthetic cart to `SaleService::checkout`: `prepareLines` reads current prices/minimums, auto-selects devices, reads current bundle composition, and may impose POS credit/shift permissions. Those differ from the immutable accepted web allocation. A real, authenticated staff actor must initiate handover; `cashier_id` currently required and should identify that actor only after the business approves its meaning for an Ecommerce sale. A proposed `SaleSource::Ecommerce` and a unique business-scoped `sales.web_order_id` (or equivalently one unique fulfillment row linking both directions) distinguish channel and prevent two sales. Do not overload `operation_key` alone as the business relationship. The sale and source web order should keep the accepted public references as immutable snapshots.

**Atomic transaction outline:** authorize actor, location and exact named action; acquire business-row mutex; lock order, payment obligation, unique fulfillment/sale link, and accepted offer/items in a documented consistent order; reject terminal/previously posted orders; validate permitted state and payment gate; compare each active reservation with accepted source line/component/device allocation; lock reservation rows, quantity pools sorted by location/variant, then device rows sorted by ID; recheck physical state, exact device condition and other active demand; insert one sale with accepted product prices, delivery charge/tax representation and genuine actor; insert sale lines and component snapshots; invoke the existing inventory posting primitives with *this order's reservation ownership*; create exactly one inventory operation/stock movement per underlying pool and sold event per exact device; transition only this order's reservations to consumed; verify before/after stock balance and every device sold; link sale, inventory operation and fulfillment record; set order to the approved handover state and append history; commit. No network call, invoice print or notification inside the transaction. Use bounded deadlock retries and return the existing linked sale for an identical retry. Any failure, including the last combo component, rolls back all rows and statuses. The unique web-order sale constraint is the concurrent retry backstop.

The current `consumeForFulfillment` is a starting safety primitive, **not sufficient as-is**. In the future implementation, its reservation validation must match the accepted offer (the existing `WebOrderStaffService::assertCompleteReservations` has related logic) and the callback contract must link sale/operation plus intended customer order state. The current `InventoryService::markDeviceSold` rejects active reservations; the current primitive transitions them before callback under the same transaction, but the new path must prove this works with real MySQL and cannot temporarily expose a sellable device to another connection. The business lock, locked device row and database unique allocation must all be validated. For combos, use the reservation rows' component variants and exact device IDs; do not call the current bundle auto-allocation path, which chooses fresh devices and current recipe. Quantity precision remains DECIMAL(14,3) and money decimal strings. The web order's one `location_id` is immutable for handoff.

## 4. Payment, shift and accounting design

**COD:** `cod_due` is an obligation, not cash. Staff phone confirmation, picking and dispatch do not mark it paid. A later dedicated collection command, available only to an authorized real collector, records when money actually reaches the business; courier handover is not collection. If a cashier takes cash, require an open shift at that location and insert one idempotent `sale_payments` cash row tied to that shift, sale and web-order collection event, then update the web payment obligation/state in the same transaction. If courier collects, hold a courier receivable/remittance state; the exact financial posting and responsible actor need approval before support. Never post pretend till cash at dispatch. A sale posted at dispatch while COD is unpaid must be represented as an Ecommerce receivable without granting generic POS credit-sale privileges or distorting credit limits; accounting design must be approved before implementation.

**Bank transfer:** `paid_verified` is set only by the existing authorized verification service. Fulfillment reads that state and the immutable decisions; it does not verify again. One uniquely linked sale payment/settlement record, if the POS ledger requires one, must reference the original verified decision(s) and carry actual verified amount and date, avoiding a second bank receipt in business reports. If payment was verified before sale posting, the bridge may materialize the sale-side record exactly once during handoff while marking it as a *projection of existing verified funds*, not a new collection. Underpaid, rejected and overpayment-review states block preparation/dispatch. The precise behavior for multiple accepted partial bank transfers and overpayments requires an accounting contract. No duplicate `SalePayment` may be created on retry. Payment verification must not silently mark an order confirmed or change accepted totals.

**Cashier shifts:** POS UI checkout requires an open shift; `SaleService` itself can accept null shift. The shift summary includes all sale payments by method but expected drawer cash uses cash only. Proposed policy: preparing/ready require no shift; actual in-store COD cash collection requires the collector's open shift; bank transfer fulfillment should not require a cash shift merely to post inventory. Whether sale creation itself must have an open shift is unapproved. If allowed without one, use null `cashier_shift_id` and a real handover actor, and add explicit storefront-channel reports so unshifted sales remain visible and reconcilable. A bank payment may appear as a non-cash method in reporting, but must not increase expected physical cash. Audit the current sales activity and close-shift reports before adopting this.

**Tax, delivery and receipt:** web accepted `total = item subtotal + delivery fee` in current source; POS `SaleService` calculates item totals and included tax from current business tax settings, and its sales schema has no delivery fee. Before bridging, approve the tax treatment and representation of a delivery charge (separate charge line/entity, not an imaginary stock variant), rounding, and how historic accepted totals reconcile to the sale and invoice. Preserve original line prices and discount snapshots even if catalog/tax settings later change. Reuse `SalePageData` and A4/thermal `InvoiceDocument` rendering once an explicit web-order receipt DTO can show the order reference, POS sale number, delivery fee, paid/unpaid truth and warranty linkage. Current receipt displays IMEI for sale lines/components; policy must decide whether IMEI appears on an authenticated issued invoice. It must **never** be added to public catalog/tracking APIs. Do not show uncollected COD as paid. Receipt printing and delivery happen after commit and can be retried without reposting the sale.

## 5. Delivery, cancellation, returns and recovery

The selected location supplies all picking. Record picker, actual reserved component/device checks, handover actor/time, destination from the immutable address snapshot, and optional carrier/reference if the business adopts one. Do not change location or substitute a serialized device after customer acceptance; changed terms require a new approved workflow. There is no existing courier integration to reuse.

Before stock posting, eligible cancellation releases active reservations in the same order transaction; current code only supports declined pending COD, so confirmed/preparing/ready cancellation requires a new approved rule. Payment evidence, `paid_verified`, and expired reservations require reconciliation, not ordinary release. After carrier handover, the sale and stock movement already exist; failed delivery, returned parcel, redelivery or customer return require custody evidence and a new authorized workflow. A returned serialized device may need inspection/condition changes; quantity goods need return-to-stock approval. Reuse `SaleService::returnSale`/`InventoryService::returnSale` only after checking their sale-line, location, refund and restock assumptions against Ecommerce delivery. Do not automatically restore available stock or issue a refund. A redelivery may reuse the posted sale but should not create a second sale or stock deduction; policy and audit fields are needed.

**Recovery guarantees to implement:** unique `(business_id, web_order_id)` sale or fulfillment link; unique fulfillment operation key with canonical payload hash; unique sale payment origin per verified decision or COD collection event; one consumed transition per reservation with stable transition timestamp; one inventory operation per web sale; immutable sale/payment rows. An outer transaction prevents ordinary partial commits. A diagnostic report should compare web order state, reservation state, sale link, stock operation, payment projection and dispatch event; ambiguous paid or physically dispatched cases go to manual reconciliation. Retry by the same operation key returns the committed result after verifying payload and ownership; a different payload conflicts. Do not repair by inserting a second sale. If printing or notification fails after commit, retry only that side effect.

## 8. Reconciliation with Phase 5 architecture

- Phase 5A proposed order states through `dispatched`/`delivered`, while the implemented reservation primitive currently jumps from `confirmed` to `fulfilled`. The future bridge must resolve this explicitly.
- Phase 5A said orders remain separate from POS sales until fulfillment; current source follows that. The unique sale link and accounting mapping are missing.
- Phase 5B.4C protects confirmed and proof-submitted orders from ordinary expiry, but no approved reservation extension exists while staff prepare/deliver. A delayed handover must not simply consume an expired allocation; define policy first.
- Bank verification is approved as a preparation prerequisite, yet source leaves bank orders `pending_confirmation`. The additional confirmation decision remains open.
- Existing POS checkout can take custom prices only through price-override controls and has no delivery-fee representation. It cannot be invoked as a web bridge without violating accepted snapshots/accounting semantics.
- Current receipt exposes IMEI to authenticated POS views; the public customer API does not. The issued invoice policy remains open.

No migration, source code, configuration, order, payment, reservation or inventory data was changed in this planning phase.

## 9. Phase 5B.5B preparation and picking source implementation (2 November 2026)

This section records a later, separately approved source increment. Sections 1–8 remain the Phase 5B.5A architecture proposal. The customer order-submission flag remains false by default. The new migration is **source only** and was not run against the active POS database.

### Named staff actions and permissions

`POST /storefront/orders/{reference}/preparation/start`, `POST /storefront/orders/{reference}/preparation/checks/{reservation}` and `POST /storefront/orders/{reference}/preparation/ready` are authenticated Inertia staff actions with server-side `storefront.prepare-orders`, `storefront.verify-picks` and `storefront.mark-ready` permissions. The additive migration grants them to the existing owner role only; ordinary POS staff do not receive them automatically. Existing `storefront.view-orders`, business scoping, assigned-location checks, CSRF and endpoint throttles still apply. All actions lock the business before the order, then reservations and underlying stock/device rows in deterministic order, in retried transactions. Starting and marking ready are idempotent on repeat. They never invoke `consumeForFulfillment`.

Preparation currently admits only `confirmed` COD with `cod_due`, a matching payment obligation, latest recorded `answered_confirmed` call, no recovery warning, complete accepted allocation and unexpired active reservations. A bank transfer remains blocked even when `paid_verified` because the additional bank-order confirmation policy is not approved. An elapsed reservation deadline returns an authorized-review error; there is no extension or invented deadline. Starting preparation changes only the order state to `preparing` and inserts append-only staff status history. No stock, reservation or payment state changes.

### Pick checks and ready gate

Additive `2026_11_02_000002_create_web_order_fulfillment_checks.php` creates business-scoped, append-only per-reservation check records with source order/item/reservation references, expected and checked DECIMAL(14,3) quantities, match/discrepancy result, optional private note, real staff actor and check timestamp. Restrictive historical foreign keys and indexes follow the existing web order schema. Rechecks insert new rows; the latest result for each reservation governs readiness. The record intentionally does not store the entered IMEI/serial value. Authorized staff enter that value from the physical device; Laravel compares it against the exact privately reserved device and its accepted condition. A mismatch is recorded as a discrepancy, never substituted. Quantity checks use the reservation's underlying component variant and accepted allocation, including combo components rather than current bundle recipe. Shared components remain separate reservation checks so each order item is auditable. Missing, consumed, released or altered allocations block the transition.

`preparing -> ready` requires a current matching check for **every** reservation and revalidates the full accepted allocation, stock pools, exact devices, conditions, payment and deadline under locks. It inserts one append-only status history event. `WebOrderRecoveryService` now treats active reservations on `preparing` and `ready` as expected, while still flagging missing or mixed allocations. Customer tracking already contains safe `preparing` and `ready` messages; private check notes, staff identity, IMEIs and internal reservation/device IDs remain outside the public tracking DTO. The staff order detail displays progress, discrepancies, preparer identity and private audit. Ready does not mean dispatched or paid.

### Verification and next gate

Focused feature tests were added to the existing staff order suite for COD preparation, call/permission/location gates, bank blocking, quantity discrepancy and recheck, a combo plus standalone line sharing component stock, exact used-device identity/condition, duplicate transitions, expired allocation, public tracking privacy, and confirmation that no sale/payment/stock movement is posted. These are database feature tests and cannot be counted as passed without a verified isolated MySQL test database; independent-connection concurrency remains unproven. Targeted PHPStan passed with zero errors; Vue TypeScript, scoped Vue checks, PHP syntax, Pint, staff route registration and the database-free Laravel unit suite (1 test) passed. The migration has not been executed. The sandbox did not permit inspecting the local TCP listener via `ss`, and an isolated MySQL test database remains unverified. Existing Phase 5 migration and POS regression verification remain outstanding.

Phase 5B.5C still requires approval of the exact stock-consumption boundary, bank-order confirmation, COD collection/courier accounting, cashier-shift behavior, invoice delivery-fee/tax mapping, and the sale bridge from sections 3–7. There is no stock deduction, reservation consumption, POS sale/payment, invoice, dispatch, delivery, refund or return in Phase 5B.5B.

## 10. Phase 5B.5C bank order confirmation source implementation (2 November 2026)

The business has now **approved** a separate, authorized staff order-confirmation action after bank payment verification and has approved physical stock consumption only at actual handover to the customer or carrier. Preparation and ready stages still leave physical stock untouched. This section supersedes the earlier “bank confirmation unapproved” statements in sections 2, 6, 8 and 9; it does not implement the handover/sale bridge. COD remains subject to its recorded `answered_confirmed` phone call and `cod_due` status.

### Bank confirmation and audit

`POST /storefront/orders/{reference}/confirm-bank` requires authenticated staff with `storefront.view-orders`, the new `storefront.confirm-bank-orders` permission, proof-view permission, and access to the order's business and fulfillment location. The additive `2026_11_02_000003_create_web_order_bank_confirmations.php` migration creates a restrictive, business-scoped one-row-per-order bank confirmation audit with staff actor/name snapshot, optional private note and timestamp. It grants the new permission to the existing owner role only. **The migration was created in source but not executed against the active POS database.** The private note stays out of customer tracking.

`WebOrderStaffService::confirmBank` uses a retried transaction and the established business-then-order row locks. It accepts only `pending_confirmation` bank orders whose order and locked payment obligation both say `paid_verified` and whose obligation amount/currency match the accepted order. It locks verification decisions, requires exactly one final `verified` decision and decimal-safe total of accepted `underpaid` plus `verified` decisions equal to the obligation, and refuses unresolved overpayment or awaiting-verification attempts. It rechecks the snapshotted reservation deadline against database time and verifies the complete exact active allocation. It then inserts the private confirmation audit, changes only the order status to `confirmed`, and appends a staff-actor status-history event with reason `bank_order_confirmed`, all in one transaction. An identical repeat finds the existing audit and returns without a second transition; a confirmed order missing the audit requires manual review. Payment amounts, payment status, proof decisions, reservations, serialized-device state and physical stock are unchanged.

The existing COD confirmation action remains separate and unchanged: it still requires an authorized recorded phone outcome, pending COD state and active allocation. Bank orders cannot use the COD route. The bank action cannot confirm COD orders.

### Preparation and customer presentation

`WebOrderPreparationService` now admits confirmed COD only with latest `answered_confirmed` call, its `phone_confirmed` status event and matching `cod_due` order/payment states. It admits confirmed bank orders only with matching `paid_verified` order/payment states **and** both the dedicated private confirmation record and `bank_order_confirmed` status event. The same payment gate is rechecked before pick checks and ready transition; complete active reservations, current stock/device facts and deadline checks still apply. No payment verification is inferred from confirmation, and no confirmation is inferred from payment verification.

The staff order page displays verified amount and review history to staff allowed to view proofs, explains that verification alone leaves an order pending, and presents a `Confirm bank order` action only when permission, payment evidence, reservation deadline and recovery checks indicate eligibility. The server remains authoritative if state changes after the page loads. Customer tracking now explicitly says a verified bank payment can still await staff order confirmation; subsequent `confirmed` and `preparing` messages use the existing safe status allowlist. Private confirmation notes, staff identities, payment proof paths, IMEIs and reservation/device IDs remain outside the customer resource. The recovery diagnostic no longer flags a successfully verified bank order merely because its initial proof deadline passed; an expired reservation still blocks confirmation.

### Verification limits and next stage
