# Phase 5B.5E2 Slice 1 — COD shop pickup handover

**Status:** Laravel source implemented 2 November 2026; database migration, feature tests and independent MySQL concurrency are **not executed**. Do not enable production order submission on the strength of source review. Read with [the E2 readiness plan](ecommerce-fulfillment-phase-5B-5E2-implementation-readiness.md) and [the accounting approval register](ecommerce-fulfillment-phase-5B-5E2A-accounting-decisions.md). Home-delivery/bank posting remains blocked by the unapproved accounting decisions there.

## Executable boundary

The first release handover action is authenticated `POST /storefront/orders/{reference}/handover/pickup`, under the existing staff web middleware, CSRF protection, `storefront.view-orders`, dedicated `storefront.handover-orders`, and `throttle:10,1`. `StaffWebOrderHandoverController::pickup` accepts only a UUID `operation_key` and decimal `cash_tendered`; `WebOrderFulfillmentService::collectPickup` resolves the business, order and one authorized shop location server-side. The new permission is granted only to the business owner by the additive migration, following existing owner permission conventions. The staff order page offers the action only for a ready COD pickup order; all eligibility is rechecked in the service.

The source uses existing `fulfilled` as the post-handover terminal order status, rather than adding a duplicate `collected` status. Customer tracking describes this as collection at the selected shop. `paid_collected` is the existing web payment state. `SaleStatus::Completed` and `SalePaymentStatus::Paid` describe the one real POS sale after physical cash collection. No sale, payment or stock mutation occurs during confirmation, preparation or ready transitions.

## Transaction and lock order

One outer `DB::transaction(..., 3)` encloses the complete posting. The service locks the business row, then the web order. It checks an existing fulfillment **before** checking mutable ready state so an identical retry after a committed response timeout returns the recorded sale. The canonical hash binds business, order, actor, mode and normalized tender; identical operation key and hash replay, while changed terms or any second key conflict. E1's unique business/order sale and fulfillment constraints are final database backstops.

For a new posting the service confirms ready/COD/pickup, then locks the real actor's user row and matching active shift through `CashierShiftService::activeId`. It re-locks the active shop location, checks the accepted pickup code/name/address/city and the physical location code/name, and rejects a non-zero fee. It locks the web payment obligation and verifies its full accepted amount is still `cod_due`; no existing COD sale-payment origin may exist. The service uses `SaleService::paymentCashDetails` for exact amount, actual tender and change; insufficient tender fails before writing.

`WebOrderPreparationService::assertReadyForHandover` rechecks recorded COD phone confirmation, separate ready state, current matching pick checks, reservation deadline, recovery diagnostics, quantity pools and exact device condition. `WebOrderStaffService::assertCompleteReservations` compares each locked reservation with the accepted offer's private allocation, including combo components. Reservation rows, stock pools and device rows are processed in deterministic location/variant/ID order. An expired reservation is rejected using database current time. Normal POS stock writers continue to enforce the reservation floor.

The service writes an Ecommerce `Sale` and accepted `SaleLine` snapshots, one cash `SalePayment` with the real `received_by` and `cashier_shift_id`, then calls `WebReservationService::consumeReadyForHandover`. This adapts the existing exact-delta primitive for `ready` without letting it set an order status independently. The callback `InventoryService::postExactWebSale` creates one sale inventory operation, exact quantity movement/device sold event, and actual cost/component snapshots. It does **not** call current-recipe combo consumption or automatic device allocation. Reservation consumption precedes physical deduction within the same transaction so the current order's allocation does not block itself; the primitive verifies final quantity deltas, remaining reservation floors and sold device states. The service then creates `web_order_fulfillments`, sets `web_order_payments` and `web_orders` to `paid_collected`, changes order state to `fulfilled`, and appends the real staff actor/reason to `web_order_status_histories`. Any exception rolls back all rows and physical updates.

`SaleService::recordPayment` and `processReturn` now lock business before actor/shift and sale, matching the business-first inventory protocol. `SaleService::checkout` blocks adding items to an Ecommerce sale. Generic sale payment and return services reject Ecommerce sale mutations server-side; sale page buttons are hidden for the same source. Normal POS sale pricing/checkout remains on its existing path. Returns/refunds for Ecommerce remain unavailable until policy approval.

## Accepted money and private device data

New orders capture immutable product SKU/barcode/tracking/combo and included **product** tax snapshots at order submission. The additive migration stores nullable snapshots to keep historical orders readable; handover refuses an older order whose required accepted snapshots are missing. Product tax uses the business's existing inclusive product tax calculation at submission, then is replayed unchanged into the sale and checked for internal consistency. No delivery-fee tax rule was added; pickup requires the already Laravel-calculated fee of exactly zero. The sale line uses accepted unit price/quantity/name and the accepted line total, even if today's catalog selling price or combo recipe changed. Inventory cost is captured from physical stock/device records at posting and does not alter accepted selling prices.

The exact device ID and IMEI remain in staff-side sale and inventory history for audit. `SalePageData::sale` suppresses line and component IMEIs for Ecommerce sale invoice data while the issued-invoice IMEI policy is unresolved; ordinary POS invoices are unchanged. Public order tracking never returns those identifiers.

## Schema added in source only

`2026_11_02_000006_add_cod_pickup_handover_snapshots.php` adds nullable product tax snapshots to `web_orders`, SKU/barcode/tracking/combo/tax snapshots to `web_order_items`, and nullable unique `sale_payments.web_cod_order_id` with a business-scoped restrictive FK. The latter is the one-collection-per-order provenance key. Rollback refuses to remove accepted tax snapshots or posted COD origins. The migration also creates `storefront.handover-orders` for the owner. `2026_11_02_000007_add_web_order_private_inventory_snapshots.php` adds the private exact allocation snapshot to order items, a composite sale/order/payment-origin FK, and a MySQL COD cash/shift CHECK. No migration was executed against either the running POS database or a test database.

E1's sale/web-order, fulfillment/order/sale/inventory operation and operation-key unique constraints, plus the new composite COD origin FK and CHECK, must still be verified on an isolated MySQL/MariaDB test database. The E1 migrations and the two new migrations are not claimed as runtime verified.
