# Rebuild and refactoring roadmap

Planning only, dated 2026-11-02. No phase is authorized for implementation by this audit. Preserve the Laravel + Vue/Inertia + MySQL + Next stack and existing data while proving business invariants. The [module matrix](module-completion-matrix.md) gives keep/refactor/rebuild decisions; the [architecture proposal](target-architecture-proposal.md) gives ownership boundaries.

## Immediate decision gates

1. Approve which customer journeys are launch scope: catalog only, COD pickup, or bank/home delivery. The working database has zero web orders, so none is accepted as operationally proven.
2. Approve the financial rules for tax, discounts, partial payments, refunds, bank transfer verification, overpayment and cash drawer treatment before Phase D/F implementation.
3. Decide whether this remains one business with multiple locations or must support independent businesses. `LocationAccessService` currently selects `setup_key=initial`; a multi-business promise requires a separate isolation project.
4. Set repair intake, custody and warranty policy before designing tables. Existing damaged-stock repair is an internal stock disposition, not customer repair management.
5. Choose a normal CI/build host and a dedicated disposable MySQL test schema. Do not run `RefreshDatabase` on the working `nalaka_mobile` database.

## Release sequence and rollback principle

Ship small modules behind existing permissions/feature gates. For every data-changing phase, take a verified backup, rehearse on a copy, compare the baseline reconciliation before and after, and retain a rollback or forward-repair path that preserves posted sale, stock and payment history. Release source refactors only after golden-master and concurrency checks prove equivalent business outcomes. Keep `STOREFRONT_ORDER_SUBMISSION_ENABLED` disabled until Phase F acceptance and operational approval.
