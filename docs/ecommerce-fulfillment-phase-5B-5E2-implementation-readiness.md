## 2. Proposed service and staff action, after approvals

Create `WebOrderFulfillmentService` as the sole web handover writer. A staff-only controller, for example `StaffWebOrderHandoverController`, should accept a server-validated UUID operation key, the already accepted order reference, the intended handover mode and the minimum approved handover evidence. Two explicit actions (pickup handover and courier handover) are clearer than a generic status editor. Authorize an actual logged-in user via a dedicated `storefront.handover-orders` permission plus business/location access. The service resolves the order by business and public reference; browser data never supply prices, payment states, stock IDs, device IDs or component choices. No customer/public endpoint posts fulfillment.

The service should return the committed sale/fulfillment on an identical retry. Store a canonical payload hash of business, order, mode and approved evidence/collection intent, excluding transient UI data. A repeated key with different payload is a conflict; a different key for an already fulfilled order returns the existing committed result only if the business operation is semantically identical, otherwise a conflict. Check the existing fulfillment **before** rejecting a now non-ready order so a timeout after commit remains retryable. Receipt printing and notifications occur after commit and cannot trigger a second posting.

### One outer transaction, bounded deadlock retry

1. Validate actor permission and assigned fulfillment location; validate request format before the transaction. Use `DB::transaction(..., 3)` around the *entire* operation, not separate commits for sale, payment, stock or history. The business row is the first mutex. The permission/location check must be repeated against authoritative rows inside the transaction.
2. Lock business, then web order by `(business_id, reference)`; check existing `web_order_fulfillments`, `sales.web_order_id` and operation-key collision. A partially linked sale without fulfillment is a reconciliation error, not permission to post another sale.
3. Require order `ready`, accepted first-release fulfillment mode, selected location/mode consistency, exact payment method, immutable totals and currency, and no `WebOrderRecoveryService::issues`. Lock the web payment obligation and applicable bank decisions/confirmation or COD call history in deterministic ID order. Require COD `cod_due` plus `answered_confirmed` and phone-confirmed history; bank `paid_verified`, exact authorized decision sum and separate bank-order confirmation. Do not mark bank money received again merely because handover occurs.
4. Require unexpired order/reservation deadlines using a database-current-time check; no silent extension. Call `WebOrderStaffService::assertCompleteReservations($order, true)` under the order lock. Lock all order reservations ordered by `(location_id, component_variant_id, id)`; reject released/expired/consumed/extra/missing rows. Compare each reservation to `web_order_items` and the accepted offer's `private_allocation`, including repeated/shared combo components and exact device IDs. Revalidate latest matching pick checks and accepted condition; reject discrepancies.
5. Aggregate quantity demand with `BigDecimal` at 3 decimals by `(business, location, component variant)` and sort those keys. Lock stock rows in that order, then serialized-device rows by ID. Recheck physical stock, other active reservation floor and exact device location, variant, status and accepted condition. The business mutex must also be honored by ordinary POS, transfer, adjustment and sale writers; test this rather than assuming every legacy path complies.
6. Build the sale from **accepted** `web_order_items` and `web_orders` snapshots, using `SaleSource::Ecommerce`, the real actor in the legacy `cashier_id`, the one accepted location, deterministic sale operation key and one `web_order_id`. Build sale lines and `sale_line_components` from the locked reservation allocations, not today's bundle recipe. Resolve actual cost snapshots without changing accepted customer prices. Enforce decimal equality: sum accepted item line totals plus approved fee/charge treatment equals accepted web total. Do not create a sale if the accounting representation cannot reconcile exactly.
7. Apply only the **approved** payment policy inside this same transaction: physical COD collection and shift linking for pickup, or verified bank receipt allocation for delivery. Set POS `paid_total`/`payment_status` from genuine allocated/collected money while leaving web order/payment states independent except for an explicitly approved COD collection transition. See §4. A payment failure rolls back the sale and all stock changes.
8. Use a deliberately adapted reservation consumption primitive that accepts `ready` and does **not** unilaterally set the customer journey state to `fulfilled`. It must transition only this order's active reservations, invoke an exact-allocation inventory poster, and verify each quantity delta and exact sold device before commit. Inventory poster creates one `InventoryOperationType::Sale`, exact operation lines, stock movements/device sold events, then updates `sales.inventory_operation_id`. It must not call `InventoryService::postSale` or current-recipe combo allocation unchanged.
9. Insert `web_order_fulfillments` only after the sale links to its inventory operation, because E1's composite fulfillment FK references `(sale_id, inventory_operation_id, business_id)`. Record real actor, handover time, approved evidence snapshot, mode, operation key and hash. Append web order status history and transition to the approved customer journey state (`dispatched` for courier, an approved pickup-handover state for pickup); `delivered` later must never create a second sale or consume again. Commit all together. No network calls or print jobs within the transaction.

**Lock-order detail:** business → order → payment/decision/confirmation and pick rows → reservations (sorted) → stock pools (sorted) → device rows (sorted) → sale/inventory/payment/fulfillment inserts. The `WebReservationService::consumeForFulfillment` nested `DB::transaction` currently reacquires business/order; future extraction should require the caller's outer transaction and held locks, avoiding a second retry boundary or divergent order. `CashierShiftService::activeId` locks the user first; if approved for COD, define a single compatible order for user/shift versus order/payment and update conflicting generic writers with regression tests. The business mutex serializes participating inventory writers, but unverified MySQL behavior and bypass paths remain rollout blockers.

### Database backstops and limitations

- Existing E1 unique `(business_id, web_order_id)` on `sales`, and unique order/sale/inventory operation/operation key on `web_order_fulfillments` prevent duplicate handovers if actually migrated. Existing `sales.operation_key`, `inventory_operations.operation_key` and active serialized-device uniqueness add backstops. They do not substitute for locked state checks.
- `sale_payments.web_bank_transfer_decision_id` is unique when non-null but allows multiple nulls. It is not a COD collection identity; do not reuse it as one. The FK does not prove that the bank decision's web order is the sale's web order. Application validation and perhaps an approval-dependent composite constraint are required.
- Existing `sale_lines` and `sale_line_components` have nullable serialized-device uniqueness scopes and business FKs. Verify exact one-to-one mapping to locked reservations in service logic; the current schema does not link every sale component to a reservation. Decide if a direct reservation-to-posting provenance FK is necessary only after a concrete reconciliation test proves the E1 fulfillment/operation identity insufficient.
- MySQL must validate CHECK support, composite FK column/index compatibility, migration order and rollback behavior on a verified isolated database. No migration status was queried for this document.

## 9. Newly identified conflicts and rollout blockers

- `WebReservationService::consumeForFulfillment` expects `confirmed`/writes `fulfilled`, but `WebOrderPreparationService::markReady` produces `ready`. The future handover cannot invoke the existing consumer unchanged.
- `InventoryService::consumeBundleComponents` recomputes current bundle recipe and auto-selects devices; that would violate accepted exact allocations. `InventoryService::postSale` must not be reused unchanged for web handover.
- `SaleService::recordPayment` locks user/shift before business while `checkout` and web inventory writers lock business first; future coexistence needs a single enforced lock order and a MySQL contention test.
- `SaleController::show` exposes generic `canRecordPayment`, `canAddItems` and `canReturn` based on permissions/status, not sale source. `SalePaymentController` calls generic `recordPayment`; web sales would need server-side restrictions to prevent an unauthorized second receipt. UI hiding alone is insufficient.
- E1 `sale_payments.web_bank_transfer_decision_id` uniqueness cannot prove the decision belongs to the sale's web order, and its nullable value cannot protect COD. `sale_payments.received_by`/`paid_at` and 100-character reference conflict with nullable original verifier and up-to-180-character customer transfer reference.
- `sales` money columns are DECIMAL(14,2), while `web_orders` totals are DECIMAL(16,2). The future writer must reject any accepted amount that cannot fit the POS schema; do not round or truncate. Quantity columns are DECIMAL(14,3) on both sides.
- E1 fulfillment composite FK requires `sales.inventory_operation_id` before fulfillment insert. Existing `InventoryService::postSale` supplies this only after physical posting; future exact poster must follow that order inside one transaction.
