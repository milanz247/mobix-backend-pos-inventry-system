## Catalog diagnosis

The reported generic catalog error was **not reproduced from the host network**. Initial sandbox HTTP requests failed and sandbox port binding failed. An approved host-context server start found port 8000 already occupied. Host-context HTTP requests then established that Laravel and Next.js were already serving successfully. The sandbox connection failure is not evidence that the user's servers were stopped.

Actual results:

- `GET http://127.0.0.1:8000/api/storefront/v1/products`: 200, `data: []`, `meta.total: 0`.
- `GET http://localhost:3000/shop`: 200 and rendered `No products found`, without the reported catalog-unavailable fallback.

- `storefront.order_submission_enabled` resolves to false.

The proven reason for the current empty catalog is missing explicit publication, not a parser mismatch or a stock filter. `StorefrontCatalogService::published()` requires active product, non-service type, published web listing, active category, active optional brand and an active variant. Stock is reported separately; products are not globally hidden just because stock is zero.

No products were created, published, repriced or stocked. Existing permission-protected staff publication is available on the product page via `PUT /products/{product}/web-listing`, requiring `products.view` and `storefront.publish`. An authorized operator must choose actual products and public slugs using that existing workflow. That is a business-data operation and was not performed under the instruction to leave existing data unchanged. After approved publication, repeat real name/price/detail/browser verification; do not treat that future verification as passed now.

## Actual communication and configuration

Catalog currently follows **browser page request → Next.js server component → server-only `lib/storefront-api.ts` → Laravel → MySQL → JSON → rendered HTML**. The browser does not fetch the Laravel catalog API. There is no existing catalog GET proxy under `app/api/storefront/v1`; those handlers currently cover delivery areas, pickup locations, offers, orders and tracking. Cart/quote browser calls use `/api/cart`, `/api/cart/items`, and `/api/quotes` proxies. No new endpoints were invented.

This is a material difference from the requested uniform catalog proxy chain; it remains unresolved. Existing server rendering does reach Laravel successfully, but it does not exercise a catalog same-origin route handler.

The existing `AppSidebar.vue` now has a permission-filtered, collapsible **Ecommerce** group with active child styling. It expands on navigation within Ecommerce, including order detail routes, using the existing shared desktop/mobile sidebar components. Existing Online Orders moved from Sales, and Delivery Areas/Pickup Locations moved from Settings; their URLs, authorization and location rules remain unchanged. No Storefront Settings page/link was invented.

`WebProductListingController` now serves `storefront/Products.vue`: 15-row pagination, name/SKU/barcode search, business-scoped category/brand choices, actual product types and Published/Not Published/Ineligible filters. Each row displays existing image, name, representative SKU, category/brand/type, POS and Ecommerce status, eligibility reasons, slug, action and publication timestamp. Publish/unpublish requires a confirmation naming the selected product, disables changes while processing, shows validation failures and uses the existing success toast.

The existing `/products/{product}/web-listing` route and product detail publication editor remain supported. The new management action reuses the same controller, validation, business scope and `web_product_listings` record, preserving existing public copy/SEO fields when only status and slug are sent. No duplicated catalog, publication table or migration was added. Existing unique business/product and business/slug constraints remain in force; repeated publication updates the same record. Publication changes are written transactionally to the existing product activity history (`updated publication`); identical repeats do not create duplicate activity entries.

`StorefrontCatalogService::eligible()` extracts the existing catalog eligibility query. The staff page and action use those same rules and explicit reasons. A proven mismatch was corrected: service products were previously accepted by the staff publication action even though the public catalog excluded them. Inactive product/category/brand, services and missing active variants are now explained and rejected. Images and positive stock were not added as eligibility requirements. A saved published listing is labeled Ineligible if current POS conditions prevent public visibility; unpublishing remains possible.

Publication covers the parent product and all active variants. Price, stock, device allocation and reservation logic are unchanged. Product/variant/stock/device full attribute snapshots are checked unchanged in the isolated tests.

### Catalog integration corrections

Added constrained GET handlers to the existing Next API proxy for categories, brands, products, product detail and availability under `/api/storefront/v1`. Next catalog reads now request these same-origin handlers; handlers call only the configured Laravel API. Filters are forwarded, cookies/credentials are not forwarded for catalog reads, error responses remain errors, backend debug messages are replaced by safe messages, and Laravel's internal pagination URLs are removed while preserving the counters consumed by existing TypeScript types.

Catalog reads and proxy responses use `no-store`, replacing the former 60-second frontend revalidation. Publication/unpublication affects the next fetch/refresh, not an already-open page without navigation. The existing product grid, detail, variants, price formatting and image fallback components are reused.

`STOREFRONT_API_URL` is now the preferred **server-only** Laravel URL, with the existing public variable retained as a compatibility fallback. `STOREFRONT_SITE_ORIGIN` identifies the actual Next URL for server-to-proxy requests (required in production; defaults to `http://localhost:3000` in development). The existing public variable still configures the approved public image origin; do not put a private production backend origin or credentials in it. `.env.example` and the setup/operation guide document these settings. Existing local `.env` files/secrets were preserved; code changes use development hot reload, so no environment restart was needed.

The existing catalog tests exposed an actual populated-catalog price-sort error: MariaDB rejected nested correlated MIN/COALESCE aggregation with SQLSTATE 42000 / error 1140. The used-device price subquery now selects its lowest existing effective price with ORDER BY/LIMIT, retaining the same device/location/reservation predicates and variant-price fallback. Tests cover both price directions and used devices with explicit and null device prices. Stock and pricing business rules were not changed.
