# Phase 5B.5D — Ecommerce handover, POS sale and accounting contract

**Status:** source-inspected design only, 2 November 2026. No migration, application code, configuration, sale, payment, reservation or stock change is authorized by this document. Read alongside [the Phase 5 order and reservation record](ecommerce-order-reservation-phase-5.md) and [the Phase 5B.5 fulfillment record](ecommerce-fulfillment-phase-5B-5.md). The later implementation records in those documents supersede their earlier open-decision proposals: actual handover is the approved stock-consumption boundary, and a verified bank payment still needs a separate staff order confirmation.

## 1. Verified source facts and blockers

| Area | Source finding | Handover consequence |
| --- | --- | --- |
| POS checkout | `SaleService::checkout` takes a real user, locks the business, checks location/shift, prepares lines from *current* variants/devices, checks current minimum-price and discount permissions, computes included tax using current `business.tax_rate`, creates a completed sale and payments, then calls `InventoryService::postSale` inside a transaction with three retries. `PosController` requires an active shift; the service's default argument does not. | Do not feed it a synthetic cart or accepted web prices. Its current-price, credit and shift rules are not a web-order accounting contract. |
| Sale identity | `SaleSource` has `in_store_pos`, `whatsapp`, `facebook`, `phone`, `other`; no Ecommerce value. `sales` has a required `cashier_id`, nullable `cashier_shift_id`, unique business-scoped operation key, sale number and inventory-operation link. It has no `web_order_id` or delivery charge. | A real handover staff actor is required. Add an Ecommerce source and a unique web-order sale link in a future additive migration. |
| Sale lines and payments | `sale_lines` hold price, discount, cost, tax, product, variant and optional IMEI snapshots. `sale_line_components` hold physical combo components. `sale_payments` are immutable, have a real `received_by`, payment method/reference/time and optional shift, but no bank-decision or COD-collection origin link. `SalePaymentStatus` is unpaid/partially_paid/paid. | Copy accepted commercial snapshots; obtain current actual cost internally. Calling the current combo path would risk different components/devices. |

The Phase 5 migrations and true independent-connection MySQL contention remain unverified per the project documents. `STOREFRONT_ORDER_SUBMISSION_ENABLED` remains false by default. No claim of rollout or locking correctness follows from this contract.

## 2. Sale bridge and minimal schema contract

Use a dedicated `WebOrderFulfillmentService` with explicit staff handover commands. It reads the accepted web order and private reservations, writes an Ecommerce sale, and coordinates inventory posting in **one outer database transaction**. Reuse sale numbering, immutable sale-line/payment models, inventory operation and stock/device event conventions; do not call `SaleService::checkout` unchanged. The bridge must neither recalculate customer prices from current catalog settings nor require a fake POS customer, cashier, shift or cart. Keep `sales.cashier_id` populated with the real initiating staff user; that field is legacy-named and the invoice label should be reviewed for web sales.

Future additive schema, after policy approval and isolated MySQL verification:

1. Add `SaleSource::Ecommerce`, `sales.web_order_id` and a unique `(business_id, web_order_id)` key with business-scoped restrictive foreign key. Sale lookup and business reporting use this direct link; duplicate sale creation is stopped in the database.
2. Add an immutable `web_order_fulfillments` row keyed uniquely by `(business_id, web_order_id)` and `(business_id, sale_id)`, with the sale, inventory operation, real actor, handover mode/time, evidence reference, canonical operation key and payload hash. This record carries the physical handover audit and exactly-once claim; the sale FK alone would not explain who handed stock to whom or whether the handover was pickup or courier. Avoid a circular FK; the fulfillment row references the sale and order, while the sale references the order. Keep history restrictive, not cascading.
3. Give the sale payment projection an immutable source link: unique bank decision ID per projected `sale_payments` row, or a separate business-scoped bridge table with unique `(business_id, web_bank_transfer_decision_id)` and `(business_id, sale_payment_id)` keys. A COD collection event needs an equivalent unique origin and operation key. Keep bank proof file paths and staff notes out of sale/customer DTOs.
4. Model delivery charge independently of stock, preferably an explicit `sale_charges` row (business/sale/type/amount/tax snapshot), with a matching sale-level delivery amount or derived total and invoice/report support. Never create a fake stocked variant. A non-stock service line is possible only if accounting, refunds, tax and reports explicitly recognize its charge type; generic current `sale_lines` require a product variant and would misclassify delivery as a product/service sale. No choice is approved yet.

Use one stable server-derived fulfillment operation identity per order, plus canonical payload hash covering order ID, handover mode, accepted total, actor authorization context and evidence identity. The unique web-order sale/fulfillment constraints are the final backstop; the operation key distinguishes an identical retry from a conflicting request. Reconcile any existing committed sale/fulfillment before checking mutable readiness or expiration so a response timeout can safely return the original result. A different payload for the same key or a second handover mode is a conflict, not another sale.

## 3. Atomic handover transaction contract

Expose only named staff actions with dedicated permission and location access. No generic status editor. This sequence applies to a customer pickup or a courier handover, once the respective accounting/evidence policy is approved.

1. Validate the real authenticated actor and location assignment. Validate handover mode, required evidence and idempotency key before entering the transaction. No browser-provided price, tax, stock, device or payment amount is authoritative.
2. Begin one Laravel transaction with bounded deadlock retries. Lock the business row first, then the web order. Look up a prior sale/fulfillment and compare canonical payload for idempotent return or conflict.
3. Lock the web payment obligation and relevant bank verification/confirmation or COD call audit. Require order state `ready`, one selected fulfillment location, current reservation validity and no reconciliation warning. COD requires the recorded `answered_confirmed` outcome and `cod_due`; bank requires `paid_verified`, verified amount equal to order due, no unresolved overpayment, and separate staff bank confirmation. Preparation and ready never post stock.
4. Lock all order reservations in deterministic order. Compare every accepted order item to its full underlying component demand, including fractional and shared combo components, and exact serialized IDs/accepted conditions. Require only active reservations belonging to this order/location and no missing, extra, released or consumed rows. Recheck latest pick evidence as appropriate.
5. Lock quantity stock rows by `(location_id, component_variant_id)` and exact device rows by ID in a fixed order. Recheck device status/location/variant/condition and quantity floors against *other* orders' active reservations. The same business mutex must coordinate POS writes and other inventory writers.
6. In the same transaction, create the sale, immutable accepted sale-line snapshots and exact combo component snapshots; assign current internal cost snapshots without altering customer prices. Use the accepted product subtotal, discount, delivery charge and total with decimal-safe arithmetic. Tax snapshots require the approval below; failure to reconcile totals blocks handover.
7. Transition only this order's reservations to `consumed`; then post the exact quantity movements and exact device sold events. Keep `WebReservationService`'s before/after movement checks and the remaining-reservation floor. Link the inventory operation, sale and immutable fulfillment record. Do not use the current combo auto-allocation path.
8. Materialize approved payment representation: verified bank decision projections once, or physical shop cash collection once if the pickup policy requires payment at handover. Courier COD does **not** insert a cash payment. Set sale paid/outstanding status from actual confirmed money while leaving web order payment truth independent; only an authorized collection workflow may change `cod_due`.
9. Append a customer-safe order status history and private handover audit. Courier handover becomes `dispatched`; customer pickup can become `delivered`/`collected` according to the approved status vocabulary. Do not set `fulfilled` merely because stock was posted. Commit. Queue printing/notifications **after** commit; their failure must not repost the sale.

Any failure, including failure on the final component or payment insert, rolls back sale, lines, payments, fulfillment link, reservation transitions, inventory movements, sold-device state and history. Commit succeeds exactly once; later delivery confirmation updates the journey only and never calls stock posting again.

`WebReservationService::consumeForFulfillment` must be adapted deliberately: its current `confirmed -> fulfilled` behavior conflicts with `ready` and the approved dispatched/delivered journey. Prefer making it an internal reservation-and-stock primitive with no order-state mutation, called by the outer bridge; retain its stock delta verification. Do not weaken existing POS checks against unrelated reservations. The implementation must verify nested transaction behavior and callback rollback on MySQL.

## 4. COD collection and courier accounting

**Customer pickup, cash physically received by shop staff.** A possible first-release flow is: real authorized staff takes cash at pickup, requires that collector's active shift at the fulfillment location, and in the same handover transaction posts sale, one cash `SalePayment`, one web COD collection event, reservation consumption and order transition. The web obligation then records actual collection; `sale_payments.cashier_shift_id` points to the real open shift, and `CashierShiftService::summary` increases expected drawer cash by the cash payment. Cash tender/change and any short payment require explicit policy and validation. A payment inserted after sale posting would need a separate idempotent collection transaction and an unpaid receivable period; do not pretend it was collected at handover. This pickup policy is **recommended, not approved**.

**Courier COD.** At courier handover the stock is posted and the sale exists, but no shop cash has arrived. The sale remains unpaid or receivable (`paid_total = 0`, `payment_status = unpaid`) until collection is reconciled; the web payment remains `cod_due`. Courier collection from the customer and courier remittance to the business are separate events. A future business-scoped courier receivable/settlement ledger must identify courier, order/sale, amount due, collection evidence, remittance amount/date/receiver and unique remittance operation; it must reconcile the same sale balance rather than create new revenue or a second sale. Only money physically received into the shop drawer creates a cash payment tied to a real collector shift. Bank remittance would be non-cash. The existing generic POS credit path is unsuitable: it requires credit/customer permissions and credit-limit rules and may create/match POS customers. Do not use it as a courier receivable shortcut. **Recommendation awaiting approval:** defer courier COD in the first release until this ledger, custody evidence and reconciliation controls exist.

## 5. Bank transfer accounting and shifts

`paid_verified` is evidence of a prior receipt, not a new receipt at handover. Lock the payment obligation plus all accepted `underpaid`/`verified` bank decisions; confirm their decimal sum equals the accepted order total, and reject unresolved attempts/overpayment review. At handover, if the POS sale ledger must reflect paid status, create one non-cash `SalePayment` projection **per accepted bank decision** using its original receipt reference, amount, verification time and real verifier as `received_by`; link each projection uniquely to its decision. The handover actor remains the sale's real staff actor, not the historic verifier. `sale.paid_total` equals the already verified sum, but source-aware reports must count the underlying bank receipt once and the sale revenue once. The projection is an allocation of existing money, never a new bank collection. Do not modify the web payment state during fulfillment. If reports cannot distinguish projection from receipt, do not enable the bridge until they can.

Shift alternatives and effects:

| Policy | `cashier_id` / `cashier_shift_id` | Reporting and drawer impact |
| --- | --- | --- |
| Shift for every Ecommerce sale | Real handover actor; active shift even for bank/courier | Simple POS workflow, but blocks dispatch without an open till and mixes channel counts into shift summaries. Bank/courier must still add zero drawer cash. |
| Shift only for physical shop cash | Real handover actor; shift on actual cash payment, nullable on bank/courier sale | Matches drawer custody. Requires storefront source reports and reconciliation for unshifted sales; bank transfer is non-cash. **Recommended, unapproved.** |
| All Ecommerce outside cashier shifts | Real handover actor; null shift | Simplifies non-cash dispatch but physical shop COD cash lacks normal drawer reconciliation; unsuitable without a separate cash-control ledger. |

The existing summary counts `sales` linked to a shift and groups `sale_payments` linked to it; expected drawer cash uses only `cash` payment/refund methods and cash movements. A web sale with null shift must remain visible in business sales reports through `SaleSource::Ecommerce`; a bank projection must not be attached to a drawer solely to make it visible. Review sale, payment, revenue and shift reports together before implementation.

## 6. Delivery charge, tax, invoice and receipt

The accepted web order preserves product subtotal, discount, delivery fee and final total. The POS sale currently has subtotal, discount, included `tax_total` and total, but no delivery-fee field or charge model. Require the decimal identity `accepted_total = accepted_product_subtotal - accepted_discount + accepted_delivery_fee`, using the actual Phase 5 offer/order snapshot definitions; compare it with sale lines plus sale charges, not today's catalog. `SaleService`'s included-tax function uses the *current* business tax rate. That would change historical accepted terms if tax settings changed between order and handover. The offer/order currently does not provide a separate accepted tax allocation, so approve delivery-fee tax treatment and capture an immutable tax basis/snapshot at offer acceptance or an explicitly governed tax reconciliation before any bridge runs. Do not silently recompute a different invoice total, and do not assume delivery is taxable or exempt. Store rounding decisions as decimal strings at line/charge level and reconcile to the sale total.

Preferred future representation is a dedicated non-stock delivery charge with its tax basis/rate and amount snapshot; adapt `SalePageData`, A4 and thermal `InvoiceDocument` to show product subtotal, discount, delivery fee, included tax where applicable, final total and actual paid/outstanding state. This keeps delivery out of `InventoryService::postSale` and allows reporting and later partial refunds to distinguish goods from shipping. A non-stock service line is a fallback only after tax/report/return behavior is specified. The printed customer invoice should include public web order reference, POS sale reference, accepted product/variant prices, handover date/mode, delivery fee, payment method and actual state. Never include private bank evidence paths or unverified COD as paid. Existing invoice code can display sale/component IMEIs, so an issued-invoice IMEI policy must be approved separately; public order tracking remains IMEI-free regardless. Printing or email occurs after commit and is safely repeatable without stock posting.

## 7. Customer journey, failure, return and recovery

Keep stock posting in the immutable fulfillment event, separate from customer journey status. `ready -> dispatched` at recorded courier custody handover; `ready -> delivered` (or a new explicit `collected` state, if approved) at physical customer pickup. Courier delivery confirmation later changes `dispatched -> delivered` without another sale, payment projection or inventory operation. A failed delivery after dispatch does not release consumed reservations. Record courier return/custody and inspect goods; use an authorized sale return/stock return if required. Do not mark a returned device `in_stock` or return quantity to available stock without inspection and an approved restock action. Redelivery of the same goods uses the existing sale and fulfillment link, never a new sale.

| Incident | Required response |
| --- | --- |
| Failure before commit | Database rollback leaves order `ready`, reservations active, no sale/payment projection/stock movement. Staff may correct and retry with appropriate idempotency key. |
| Duplicate request or response timeout after commit | Resolve unique sale/fulfillment by order and operation key; identical payload returns the committed result, conflicting payload returns conflict. Do not re-run posting. |
| Notification/printing failure after commit | Retry only the after-commit side effect; the sale and handover remain committed. |
| Courier delivery failure/parcel returned | Record custody and manual review. Sale and consumed reservations remain historical; no automatic stock restore or refund. |
| Customer return after delivery | Evaluate `SaleService::processReturn` and `InventoryService::returnSale` against web customer identity, charge allocation, original location, serialized condition and COD/bank refund assumptions. Require approved return/refund policy before invoking. |

Future read-only diagnostics should compare order status, fulfillment event, sale link, sale payment origins, reservation statuses, inventory operation and device events. An ambiguous physically handed-over or bank-paid order goes to manual reconciliation; no automated second sale, release, refund or stock reset.

## 8. Decisions requiring explicit business approval

The stock-consumption boundary and separate bank confirmation are already **approved** and are fixed in this contract. Every recommendation below is **unapproved**.

| Decision | Options and technical effect | Safe recommendation, unapproved |
| --- | --- | --- |
| 1. Customer-pickup COD collection | Collect full cash in handover transaction vs later separate collection; changes sale paid state and rollback scope. | Collect full amount at pickup in the atomic handover, with real collector and shift. |
| 2. Courier COD and remittance | Courier receivable with later reconciliation vs unsupported; affects unpaid sales, custody, settlement and reporting. | Defer courier COD until receivable/remittance ledger and accountable courier flow exist. |
| 3. Shift requirement | Every sale, physical shop cash only, or no web shifts; affects dispatch availability and drawer accountability. | Require open shift only when staff physically receives cash. |
| 4. Non-cash Ecommerce reporting | Attach bank sales to shifts vs source/channel report; affects shift counts and bank double counting. | Source-based web sale and receipt reports outside drawer cash. |
| 5. Delivery-fee tax | Taxable, exempt or conditional; affects accepted tax snapshot and invoice liability. | Obtain accounting/legal decision; block bridge until configured per business. |
| 6. Delivery-fee invoice representation | Dedicated charge vs typed non-stock line; affects reports, partial returns and inventory. | Dedicated sale charge with tax snapshot and no stock movement. |
| 7. IMEI on issued invoice | Show on authenticated issued invoice or staff-only document; affects warranty proof and privacy. | Allow only on controlled issued document if business approves; never public tracking. |
| 8. Courier handover evidence | Signed custody, scan, carrier reference or manual record; affects dispute resolution and idempotency payload. | Require real actor, timestamp, carrier and reference/evidence before courier handover. |
| 9. Customer pickup support | First release vs later; affects delivery fee, area selection, location and receipt flow. | Enable only with an explicit pickup offer and zero/defined fee contract; do not repurpose delivery offers. |
| 10. Failed delivery/parcel return | Inspection hold, automatic restock or redelivery; affects sale return, device condition and refund. | Inspection hold and manual reconciliation, with separately approved redelivery/return actions. |

Still unresolved in prior documents: numeric reservation/COD/proof deadlines, reservation extension while preparing/ready, customer cancellation cutoff, warranty start, return/refund terms and evidence retention. The bridge must fail closed on an expired allocation; it must not invent an extension or expiry. These policies do not change the approved handover boundary.

## 9. Future tests and implementation stages

**Tests required before rollout:** single quantity handover; accepted price and tax snapshot; exact serialized device/condition; combo and mixed standalone/combo shared components; final-component failure rolling back all earlier writes; active reservation consumed exactly once; unrelated POS reservation protection; business/location/actor permission denial; duplicate sequential and concurrent handover; unique sale and fulfillment constraints; response-timeout retry; bank verified partial decisions projected once without duplicate receipt; overpayment/unpaid/underpaid gates; COD shop cash exactly once with expected drawer amount; courier COD unpaid/receivable and later remittance without second revenue; delivery charge and invoice arithmetic; IMEI policy; notification failure after commit; failed delivery and sale-return boundary. Prove POS-versus-handover contention and duplicate handover using independent MySQL connections/processes. Sequential or SQLite tests do not prove row-lock correctness.

**Recommended sequence:** (1) isolated MySQL migration, rollback, regression, scheduler and concurrency validation of existing Phase 5 source; (2) approve the ten accounting/operational decisions and tax/TTL policies; (3) additive sale/fulfillment/payment-origin/charge schema plus source/reporting and invoice contract; (4) dedicated web handover service and exact-reservation inventory posting with bank payment projection; (5) approved shop COD cash collection and shift reconciliation; (6) courier COD ledger and custody, if approved; (7) invoice issuance, delivery exceptions, returns/refunds and end-to-end rollout verification. Keep customer order submission disabled until the earlier rollout blockers and this bridge's tests are resolved.

## 10. Phase 5B.5E1 source foundation (2 November 2026)

**Approved first-release combinations:** `bank_transfer + home_delivery` and `cod + shop_pickup`. Courier COD and bank-transfer pickup are unavailable. Bank home delivery retains proof verification, separate staff order confirmation, preparation, and later physical stock consumption at courier handover. COD pickup retains the recorded phone confirmation and `cod_due` until cash is physically collected at the shop handover. Courier delivery confirmation never reposts stock. These approved rules supersede the broader options in section 8; delivery-fee tax, sale charge posting, payment projection, cashier shift and invoice details remain for later approval/implementation.

**Additive schema created in source, not executed:** `2026_11_02_000004_add_web_sale_bridge_foundation.php` adds nullable `sales.web_order_id`, unique business/order and composite same-business FK, plus unique sale/order/business and sale/inventory/business keys for fulfillment FKs. Existing POS sales keep `NULL`. A MySQL CHECK and Eloquent save validation require Ecommerce source and a web-order link to appear together. `SaleSource::Ecommerce` is an added enum case; the ordinary POS source selector and checkout request explicitly exclude it, preserving the existing POS sources. The new `web_order_fulfillments` table holds exactly one order/sale/inventory-operation handover identity, actor, mode, posted status, operation key/hash, time and optional evidence reference. Its business-scoped FKs require matching sale/order, sale/inventory operation and order/mode; restrictive deletes and unique order, sale, inventory operation and operation key constraints prevent duplicate identities. No code creates a fulfillment row in this phase.

**Payment provenance foundation:** nullable `sale_payments.web_bank_transfer_decision_id` has a unique key and same-business FK to an existing bank decision. It represents a future *projection of a previously verified receipt*, never a second receipt. The migration does not insert a sale payment or change a bank decision. The eventual bridge must check decision status, amount, order ownership and actual reporting treatment before inserting a projection. COD collection needs a distinct, uniquely linked collection event; no COD collection schema or payment writer is added yet. No courier receivable/remittance structure is added.

**Accepted mode snapshot and API contract:** nullable `fulfillment_mode` is added to offers/orders so historical rows remain readable; new offers require it, and new submission rejects a missing or incompatible mode. The accepted terms digest now includes the mode and, for pickup, the selected shop code/name. Home delivery requires a delivery-area code and address and uses the existing server-calculated area/mapping fee. Shop pickup requires an active same-business location of type `shop`, identified by code and revalidated by Laravel; it has no delivery area/address and a `0.00` delivery charge. The offer service still validates whole-cart availability at that location. New public offer/submit/tracking responses expose only the mode and safe pickup location code/name; no internal location ID, device ID or stock count. A changed pickup location or mode requires a fresh offer and explicit acceptance. Older accepted orders with a null mode are readable but cannot enter the new handover flow without a separately approved historical reconciliation process.

**Compatibility gate:** the existing Next.js checkout currently sends a delivery-area request without `fulfillment_mode`. It will receive validation errors until a separately approved Next.js mode and pickup-location UI is added. This phase deliberately leaves `Ecommerce/` unchanged and leaves customer order submission disabled. E2 must add a safe public shop-location selector or equivalent validated UI; an arbitrary browser-supplied location ID must never be accepted. It must also handle null delivery area for pickup and clearly show pickup terms. This is an integration blocker, not a reason to silently infer the customer's mode from an old payload.

**Verification on this date:** targeted PHPStan passed with zero errors; Pint passed for changed PHP files; the database-free unit suite passed 2 tests and 7 assertions, including the first-release mode policy. New feature tests cover mode acceptance/rejection, legacy null mode, source compatibility, business-scoped sale linkage, one-sale/one-fulfillment uniqueness, operation-key uniqueness and bank-decision provenance. An attempted five-test feature run against isolated SQLite `:memory:` failed **before any assertions** in the pre-existing `create_locations_table` migration because SQLite does not implement its `IF(...)` generated-column expression. Local `mysqladmin ping` could not access `/run/mysqld/mysqld.sock`, and an isolated disposable MySQL test database has not been verified. The new migration was created but **not run or rolled back**; no real sale, payment, fulfillment, reservation or stock record was written. MySQL/MariaDB FK/CHECK behavior, rollback, existing POS regressions and independent-connection contention remain unproven.

**Phase 5B.5E2 boundary:** verify the migration and all feature/regression tests on an isolated MySQL database first. Resolve approved pickup discovery and Next.js contract in its own authorized phase. E2 still needs explicit delivery-charge/tax representation, payment projection and COD collection accounting, cashier shift policy, handover actor/evidence controls, invoice contract, and a dedicated atomic service that adapts `WebReservationService::consumeForFulfillment` to the `ready` state. Do not enable order submission, consume stock, create sale payments, or invoke the sale bridge from this E1 foundation.
## Phase 5B.5E1C — Pickup location configuration and public contract

This section supersedes the pickup-discovery blocker described in the E1 compatibility gate above. The public Laravel pickup-location endpoint now exists in source; customer selection in Next.js and isolated MySQL verification remain outstanding.

**Implemented in Laravel source only; migration not executed.** Additive migration `2026_11_02_000005_create_web_pickup_locations.php` introduces business-scoped `web_pickup_locations`. Each row links one existing location to a unique public code, optional customer-facing name and selection priority. New rows are inactive by default. The same-business location foreign key is restrictive, and unique keys prevent duplicate business/location or business/public-code mappings. No product, stock or location data is copied. Nullable pickup address and city snapshot fields were added to offers and orders; existing historical rows remain readable. Rollback refuses to discard accepted pickup history.

`storefront.manage-pickup-locations` protects `/settings/storefront-pickup`. The owner receives this permission through the additive migration; other staff need an explicit grant. The Vue/Inertia settings page lists only locations the actor may access. Staff may assign a public code, optional display name and priority, and enable or disable pickup. Only an active `shop` location can be enabled. Disabling a mapping preserves its row and existing offer/order snapshots. Settings updates acquire the established business-row mutex before changing the mapping.

`GET /api/storefront/v1/pickup-locations` uses the existing catalog throttle and returns `{data: [{code, name, address, city}]}` with `Cache-Control: private, no-store`. It lists only explicitly enabled mappings whose same-business location is an active shop, ordered by priority then public code. `address` and `city` come from the existing location record; no hours, telephone, internal IDs, priority or stock details are exposed. An active warehouse or unmapped shop is never public by default. This list is advisory: offer creation checks current whole-cart availability at the selected location.

For `cod + shop_pickup`, `POST /api/storefront/v1/order-offers` now resolves `pickup_location_code` as the **public mapping code**, never a location ID or an implicit location code. It rejects a disabled, inactive, warehouse or foreign-business mapping. It evaluates the entire cart at that exact location using the existing shared-demand/availability and serialized-device selection logic. If the chosen shop cannot fulfill the cart, it returns `409 PICKUP_LOCATION_UNAVAILABLE` without trying another shop. Pickup has a Laravel-calculated `0.00` delivery fee. The customer-safe offer contains the public pickup code, name, address and city; the terms digest and immutable offer snapshot include those details. Home-delivery selection and fee logic are unchanged.

Order submission re-resolves the same active pickup mapping inside its existing business-locked transaction, checks its internal location and public code/name/address/city against the accepted offer, and rejects changed or disabled terms as `409 OFFER_STALE`. It then runs the existing full-cart stock, exact-device and atomic reservation checks. It copies accepted pickup snapshots to the order; later location edits do not rewrite committed history. The tracking and submission resources expose only customer-safe pickup snapshots. Existing pre-migration pickup offers without an address snapshot will require a fresh offer if they are still unexpired after deployment; no accepted price or location is silently changed.

**Verification:** PHP syntax, focused PHPStan, Pint and Vue TypeScript checks passed. The database-free Unit suite passed 2 tests with 7 assertions. Database feature tests were updated/added for public filtering, permissions, uniqueness, selected-shop availability, mapping deactivation, offer non-mutation and immutable snapshots, but were not executed because an isolated MySQL test database has not been verified. ## Phase 5B.5E1D — Next.js pickup selection integration

The Next.js same-origin `GET /api/storefront/v1/pickup-locations` route forwards to Laravel through the existing server-side storefront proxy. It returns only Laravel's public `code`, `name`, `address` and `city` fields in `{data: [...]}`; internal location/business identifiers, stock and staff fields are removed. Responses use `Cache-Control: private, no-store`. The public pickup list does not require or forward a guest cart token. Laravel's existing catalog throttle still applies.

Checkout now loads pickup shops from that proxy. `shop_pickup` selects a public `pickup_location_code` and fixes payment to `cod`; `home_delivery` retains `delivery_area_code`, address and `bank_transfer`. Empty or failed pickup lists block pickup offer creation and provide a retry. The browser requests a fresh indicative quote before every order-ready offer, and forwards the selected public code through the existing same-origin offer proxy. It sends no price, fee, stock or internal location identifier. Switching mode, changing the shop or delivery area, changing contact/address details, or editing the cart clears the displayed offer, accepted digest and submission attempt, so the customer must obtain and accept new terms. The Laravel terms digest includes the pickup snapshot. Offer review displays Laravel's selected shop, optional address/city, accepted prices, Laravel-calculated fee and expiry; it does not calculate totals in React. Offer creation does not place an order or reserve inventory.

The confirmation and authenticated tracking proxies now allowlist pickup address and city from Laravel's immutable order snapshots. Their pages show the selected shop and available address/city, COD due status, phone-confirmation requirement and cash-at-handover instructions. They do not expose internal location IDs or device details. The order submission proxy, idempotency key and per-order HttpOnly credential cookie were not changed. The existing Place Order action remains subject to Laravel's disabled-by-default `STOREFRONT_ORDER_SUBMISSION_ENABLED` gate.
